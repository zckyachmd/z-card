# Architecture and decisions

## Before and after

Before: one force-dynamic page with client-heavy sections, anchor navigation, multiple analytics integrations, Bun installation with pnpm lockfile, and Chromium tests against next dev.

After: static Server Component pages for home, biography, project indexes/details, journal, privacy and syndication. Contact remains dynamic for runtime SMTP and Turnstile configuration. Small Client Components own menu state, themes, consent, contact submission, code copying, digital cards and the skill-tree playground. No global state library or CMS.

## Boundaries

- `src/app`: routes, metadata, feed and sitemap.
- `src/components`: shared UI and focused browser interactions; existing Radix primitives remain available.
- `src/config`: public site identity and curated project data.
- `src/lib`: content validation/reading, metadata helpers, analytics event boundaries, SMTP, abuse prevention.
- `content/articles`: trusted local Markdown with adjacent schema-validated JSON metadata.

React Markdown parses content without evaluating JavaScript or MDX expressions. Raw HTML is skipped. GFM tables, heading IDs, syntax highlighting, and copying are supported. The same GitHub slug algorithm generates heading IDs and the table of contents. Source is trusted repository content; there is no remote compilation endpoint.

## Decisions

1. **Node 24 LTS / pnpm 10.34.7.** Node's official release table identifies 24 as LTS and 20 as EOL as of the audit. Existing pnpm lockfile wins over an unproven Bun migration. Docker installs and runs the same runtime family, with frozen installation.
2. **Next 16.4.2 / React 19.3.1.** Registry engine and peer requirements were checked; production build and tests validate actual integration. Next ESLint tooling is aligned to 16.4.2. ESLint 9 remains because Next's transitive React/import/accessibility plugins do not declare ESLint 10 compatibility; its support limitation is recorded rather than hidden by peer overrides.
3. **Safe Markdown over executable MDX.** File-based authoring meets the publishing need without arbitrary content code execution. Metadata and body are separate for explicit validation and predictable tooling.
4. **Rebuild on publication.** Published routes, RSS and sitemap share one filtered content source. Draft/future content is excluded everywhere. Scheduled dates require a build on or after publication; there is no background CMS or scheduler.
5. **Consent-first GA4 only.** Always-on Vercel Analytics and Speed Insights were removed; Umami no longer injects scripts. Parallel trackers added no required value and risked redundant collection.

## Operational constraints

Rate limiting is process-local and trusts sanitized forwarding headers. The reverse proxy must overwrite untrusted client forwarding headers. Multi-replica deployments need ingress/distributed limiting. The optional SMTP sender must be tested against an isolated mail service before enabling real delivery. No mail is generated by load tests.

The article fixture switch only recognizes `CONTENT_DIRECTORY=tests/fixtures/articles`; normal builds always read `content/articles`. It exists to validate a real production article route without publishing fabricated writing. Never deploy the fixture build.

The complete dependency audit retains one development-only high advisory in `braces`, transitively required by Next's ESLint glob tooling, with no patched version offered by the registry at verification time. It is not in production dependencies and no user-supplied patterns are passed to the linter. Do not describe this as a clean all-dependency audit. Recheck upstream before changing the tooling baseline.
